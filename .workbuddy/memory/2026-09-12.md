# 2026-09-12

## 实现：反序列化后释放类型树（内存优化 P0）
- 背景：整堆诊断显示 `TypeTreeNode` 占托管堆 ~32.4%（4652 万实例）、`TypeTreeNode[]` ~3.7%，类型树元数据合计 ~41%，且反序列化后成死重（仅 `GameAssetFactory.ReadMonoBehaviour` 读 `OldType`，导出不读；无"原样回写 SerializedFile"产品路径）。
- 改动：
  - `AssetRipper.IO.Files/SerializedFiles/SerializedFile.cs`：新增 `ReleaseTypeTrees()`（清空每个 `SerializedType`/`SerializedTypeReference` 的 `OldType.Nodes` 与 `StringBuffer`）与静态开关 `ReleaseTypeTreesAfterDeserialization`（默认 `true`）。
  - `AssetRipper.Assets/Collections/SerializedAssetCollection.cs`：在 `EnsureAssetsLoaded()` 全量反序列化完成后（循环末尾）调用 `file.ReleaseTypeTrees()`（受开关控制）。
  - 开关放在 `SerializedFile` 而非 `GameAssetFactory`，避免 `AssetRipper.Assets` → `AssetRipper.Import` 的反向依赖。
  - `TypeTreeExtractor`、`JsonSerializer` 两个工具在 `Main` 入口设 `ReleaseTypeTreesAfterDeserialization = false`（它们直接读 `OldType`，且走原始 SerializedFile 不触发集合加载，纯防御性）。
- 验证：`dotnet build AssetRipper.Assets.csproj -c Debug` 通过，0 错误 0 警告。
- 风险/边界：`UnloadAssets` 后若重新反序列化会丢失 MonoBehaviour 结构（退回 UnloadedStructure）；但工程内 `UnloadAssets` 无调用方，常规流程安全。需要原样回写 SerializedFile 或重读时设 `SerializedFile.ReleaseTypeTreesAfterDeserialization = false`。

## 补充（同次会话后续）：解析期释放非 MonoBehaviour 类型树
- 复查确认 `OldType` 在产品内仅 `GameAssetFactory.ReadMonoBehaviour` 读取，且只对 MonoBehaviour（`RawTypeID == -1` / `ScriptTypeIndex >= 0`）类型使用；所有引擎类型（Transform、MeshFilter…）在解析后永不被读取。
- 在 `SerializedFile.SetProperties` 解析完成后新增 `ReleaseUnusedTypeTrees()`：立即清空非 MonoBehaviour 类型的 `OldType.Nodes`/`StringBuffer`。
- 收益：在**加载期**就削掉绝大多数 `TypeTreeNode`（避免大游戏 OOM 的真正瓶颈），而 P0 的 `ReleaseTypeTrees` 仍负责反序列化后清掉剩余 MonoBehaviour 树。
- 比"跨文件去重"更安全：无共享树，因此不与 P0 的按集合释放冲突（去重需协调全局统一释放，风险更高）。
- 构建验证：`dotnet build AssetRipper.IO.Files -c Debug` 通过，0 错误（仅有 SerializedFileMetadata.cs 既有 `_stream` warning，与本次无关）。
- 工具（`TypeTreeExtractor`/`JsonSerializer`）已在 Main 设 `ReleaseTypeTreesAfterDeserialization = false`，故不会触发该释放。

## 补充（同次会话）：释放 TypeTreeNode[] 底层数组（修复 Clear() 不缩容）
- 现象：P0 + 解析期释放后，`TypeTreeNode` 单对象已消失，但 `TypeTreeNode[]` 仍以 #3 / 363.8 MB（数量 387086，与优化前一致）残留。
- 根因：`List<TypeTreeNode>.Clear()` 仅把 Count 置 0，底层 `TypeTreeNode[]` 数组仍被 `_items` 持有（Capacity 不变），故数组不被 GC 回收。
- 修复：在 `TypeTree` 新增 `Reset()`（Clear 后将 `Nodes.Capacity = 0`，使 `_items` 指向共享空数组 s_emptyArray，原数组脱引用可 GC；并清空 StringBuffer），`ReleaseUnusedTypeTrees` 与 `ReleaseTypeTrees` 改调 `type.OldType.Reset()`。
- 构建验证：`dotnet build AssetRipper.IO.Files -c Debug --no-restore` 通过，0 错误（仅 SerializedFileMetadata.cs 既有 `_stream` 警告）。
- 预期收益：诊断后 `TypeTreeNode[]` 应从 Top25 消失，再省约 363.8 MB（需重跑 Nikki4 提取确认）。
- 剩余表面：`SerializableTreeType` #5（307MB）、`SerializableType+Field[]` #10（201.8MB）、`Free` 碎片 #8（232MB/90552 块）——来自 GameAssetFactory 重建 MonoBehaviour 结构，P3 高风险项，暂不动。
