## ComputeShader 源码还原导出（ComputeShaderExportMode）

**需求**：ComputeShader 导出能否像 Shader 还原那样得到可读代码。实测结论：Nikki4 的 ComputeShader 每个 kernel 的 `code` 字段**内嵌的就是 HLSLcc 生成的 GLES GLSL 文本源码**（hex 编码在 YAML 里），与 Shader 侧「随包不含编译字节码」同一事实——无需反编译，hex 解码即源码。`E:\Project\Unity\Nikki4\Assets\ComputeShader\*.asset` 16 个文件全部 kernel 载荷均为文本（已实测解码 `VFXCopyBuffer.asset` 验证 `#version 310 es ... void main()` 完整源码）。

**实现（新增导出模式 `ComputeShaderExportMode{ Yaml, Source }`）**：
- 新增 `ComputeShaderExportMode.cs`（`AssetRipper.Export/Configuration`）；`ExportSettings.ComputeShaderExportMode` 默认 `Yaml`（保持原 .asset 行为），`Source` 模式在 `ProjectExporter.Overrides.cs` 注册 `ComputeShaderSourceExporter`。
- 新增 `Shaders/ComputeShaderSourceExporter.cs`（遍历 `IComputeShader.Variants[].Kernels[]`，`#pragma kernel` + `#pragma numthreads` + 载荷；`IsLikelyText` 前 512 字节 ≥90% 可打印判定文本直通，否则注释标记二进制载荷）+ `Shaders/ComputeShaderExportCollection.cs`（扩展名 `compute`；meta 用 `ComputeShaderImporter_*` 版本类，19 段版本切换，pathID=0）。
- UI：`ComputeShaderExportModeDropDownSetting`（GUI.Web）+ `SettingsPage.g.cs` 手工补 `SetProperty` case 与 `WriteDropDownForComputeShaderExportMode`（预生成静态文件）+ `SettingsPage.cs` 挂到脚本/导出格式行空位。
- 本地化：en_US.json 5 键插在 `commands` 之后（ordinal 顺序：export_title < format_source < format_source_description < format_yaml < format_yaml_description）；zh_Hans.json 插在 shader 键后（CRLF 保持）。
- CodeWiki.md 第 7 节加「ComputeShader 源码还原」小节。

**关键接口事实（反射核实 SourceGenerated 1.3.14.2）**：
- `IComputeShader`：`Variants: AccessListBase<IComputeShaderVariant>`（Nullable 标注）、`Name_R: Utf8String`；`IComputeShaderVariant`：`TargetRenderer/TargetLevel/Kernels`（Kernels 为 Nullable 标注）；`IComputeShaderKernel`：`Name_R_Utf8String`/`Name_R_FastPropertyName`（class）、`Code: byte[]`、`ThreadGroupSize: AssetList<uint>`（3 值 = 64,1,1 小端）、`PreprocessedSource`。
- `ComputeShaderImporter` 无静态 `Create` 门面（区别于 `ShaderImporter.Create`），需自写版本切换；各版本类字段完全一致，切换仅为 meta 形状对齐。
- `.compute` 文件 Unity 用 `ComputeShaderImporter` 接管，meta 节点为 `ComputeShaderImporter`。

## 性能：`InitializeAllDependencyLists` 在 30 万文件下耗时数小时 → 已修

**根因（两层）**：
1. **主因：解析路径每层都线性遍历全部子 Bundle。** 原 `Bundle.ResolveInternal` 每层走 `TryResolveFromCollections`（自身集合字典，O(1)）+ `TryResolveFromChildBundles`（**遍历该层全部子 Bundle**、对每个查它的自身字典）。树是“根 + 30 万个子 Bundle（一个 bundle 文件一个）”，于是**单次解析 = K 次字典查询**（K=30 万）。解析次数 = 集合数 × 依赖数 × 2（name/fixedName），合计上亿次 → 数十亿到上千亿次查询。基准实测：30 万子 Bundle 下单次解析 **9.6 ms**，30 万次解析外推 **48 分钟**（单依赖项）；依赖项多个即数小时——与用户现象吻合。
2. **次因：缺失依赖逐条打日志。** `ReportMissingDependency` → `Logger.Warning`，而 GUI 同时挂了 `ConsoleLogger` + `FileLogger`，后者每条都 `File.AppendAllText`（重开文件）。海量缺失依赖时日志本身是小时级瓶颈。

**改动（`Source/AssetRipper.Assets/Bundles/Bundle.cs`）**：
- 把“每个 Bundle 一个仅含自身集合的字典”改为**“一层”索引**：`_levelCollectionsByName` = 自身集合 + 直接子 Bundle 的集合（自身优先、子 Bundle 按序、首个匹配优先），恰好等价于原来的两步查询。`ResolveInternal` 变成“逐层一次哈希查表”，代价 = 树深，**与子 Bundle 数无关**。
- 阈值 `MaxLinearLevelEntryCount = 8`：一层条目 ≤8 时线性扫描**不建字典**（省掉几十万个微型字典的分配与常驻内存）；条目数用 `_levelCollectionEntryCount` 缓存（`NotCounted = -1` 哨兵，注意 0 是合法值）。
- 资源解析同病同治：`_levelResourcesByName`（键为 `NameFixed`），`ResolveResource` 每层 `level ?? ResolveExternalResource`。
- **索引失效**：`AddCollection`/`AddResource` 失效自身 + 父（父的一层索引含本节点的条目）；`AddBundle` 失效自身；`Dispose` 再补一次 + 父。不能只做增量 `TryAdd`——新条目在“一层”顺序里位于子 Bundle 之前，同名时会输给已登记的子里条目（语义会变）。
- 内存有界：全树索引条目 ≤ 2 × 集合总数，比原方案更省。
- `ResolveCollection(string)`：`fixedName == name` 时跳过第二次 `ResolveInternal`（`FileIdentifier.PathName`/集合名在读取时已 Fix 过，第二次纯重复）。
- `InitializeAllDependencyLists` 加 `DependencyInitializationContext`：用 `DeduplicatingDependencyProvider` 装饰器按 `identifier.GetFilePath()` 去重缺失依赖（逐条打印上限 1000、去重统计上限 10000）+ 每 5 万集合打一次进度 + 收尾汇总一行。

**性能基准（`.workbuddy/tmp/bundlebench/`，可复用）**：临时 console 工程 ProjectReference 到 `AssetRipper.Assets`，用 `ProcessedBundle`/`ProcessedAssetCollection` 造树，并**在工程内复刻旧实现**做 A/B（同进程、同数据、同命中数）。用法 `dotnet run -c Release -- <子Bundle数> <每Bundle集合数> <采样次数>`。
- 2 万子 Bundle × 10 集合（20 万集合）：旧 611 µs/次 → 新 0.9 µs/次；外推 122 s → 0.2 s。
- **30 万子 Bundle × 1 集合（= 用户口径）：旧 9594 µs/次 → 新 0.6 µs/次（约 16000 倍）；外推 48 分钟 → 0.2 秒；根索引构建 25.7 ms；两侧命中数完全一致。**

**验证**：全解决方案 `dotnet build AssetRipper.slnx --no-restore` **0 error CS**（仅有 MSB3021/MSB3027——`AssetRipper.GUI.Free` PID 27492 正在运行占用 `0Bins/AssetRipper.GUI.Free/Debug` 的 DLL，复制步骤失败，非编译问题）。`dotnet test AssetRipper.Assets.Tests`：FileResolutionTests **24/24 通过**（新增 5 个：自身优先于子、兄弟取首个、只向下探一层、资源兄弟取首个、**索引失效后重建**）。
