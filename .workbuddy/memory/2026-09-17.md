# 2026-09-17

## 排查：Nikki4 全量导出在 10374/725277 处 OOM 崩溃

**结论：崩溃点（FastPng 的 `fpng_encode_image_to_memory` 原生分配）只是压垮骆驼的最后一根稻草，根因是托管堆膨胀到 ~59 GB（物理内存仅 32 GB）。**

证据（来自 `Source/0Bins/AssetRipper.GUI.Free/Debug/AssetRipper_20260916_220724.log`）：
- 阶段托管堆：加载后 5950 MB → 懒加载完成 5402 MB → 6266 MB → **OriginalPathProcessor 后 42908 MB（+36.6 GB）** → **EditorFormatProcessor 后 58613 MB（+15.7 GB）** → Process 完成 59055 MB → Export 前 59061 MB → 崩溃。
- ClrMD 整堆快照：561,204,450 个对象 / 51188 MB；AssetRipper 命名空间占 19907 MB（4.54 亿对象）；`Free` 空洞 8467 MB（16.5%，LOH 碎片）。
- 主要类型：`System.Byte[]` 3697 万 / 14548 MB、`AnimationCurve_Single_2018` 2924 万、`AssetList<Keyframe_Single_2018>` 2924 万、`ColorRGBAf` 3698 万、`Utf8String` 3796 万、`SerializableStructure`/`SerializableValue[]` 各 3093 万。
- 工作集在阶段诊断间跌到 15~243 MB → 系统级内存压力极大、全程换页（导出 10374 个集合耗时约 11 小时）。
- 机器：32 GB RAM + 56 GB 页面文件；64 位进程（PE machine=0x8664）；Server GC 开启。

**两处"懒加载被击穿"的代码（都是 fork 自己改造过、但漏掉的分支）：**
1. `AssetRipper.Processing/Scenes/OriginalPathProcessor.cs` 的 `SetOriginalPaths(IAssetBundle)` / `SetOriginalPaths(IResourceManager)`：
   `kvp.Value.Asset.TryGetAsset(bundle.Collection)` → `AssetCollection.TryGetAsset(pathID)` 内部调 `EnsureAssetsLoaded()` → 整集合全量反序列化。同类里其它地方已改用 `EnumerateAssetMetadata()` + `TryGetAssetOnly()`，只有这两条容器路径没改。
2. `AssetRipper.Processing/Editor/EditorFormatProcessor.cs` 的 `GetReleaseAssets()`：`GetReleaseCollections(...).SelectMany(c => c)` → `AssetCollection.GetEnumerator()` 调 `EnsureAssetsLoaded()` → 全量反序列化（且顺序 + 并行各枚举一次）。

**但注意：导出阶段本身必然全量物化**（`ProjectExporter.CreateCollections` / `ProjectAssetContainer` 都用 `fileBundle.FetchAssets()`），所以仅修懒加载只能压掉 Process 阶段的重复物化，不能把峰值降到 32 GB 以下。

## 其他观察
- 导出循环 `ProjectExporter.Export` 里 `collection.Export(...)` 没有任何异常隔离：单个资产抛异常即中断整场导出（本次损失约 11 小时）。
- `Logger.LogMemoryDiagnostics` = 强制双轮 GC 后读 `GC.GetTotalMemory(false)` 与 `Environment.WorkingSet`；工作集数值可用来判断系统级内存压力。
- 日志文件位于 exe 同目录 `AssetRipper_yyyyMMdd_HHmmss.log`，保留最近 5 个；无时间戳，按行号推断阶段。

## 已实施：P0-1 导出循环异常隔离（方案文档 §六 有完整记录）
- `ProjectExporter.cs`：循环内 try/catch（OOM 与一般异常分开）、新增私有嵌套类 `ExportFailureTracker`（按异常类型聚合、失败样例、汇总；连续 5 次或累计 20 次 OOM 熔断；OOM 后做 `GCSettings.LargeObjectHeapCompactionMode = CompactOnce` + 双轮 GC；同类异常仅首条带完整堆栈）。熔断时仍触发 `EventExportProgressUpdated`/`EventExportFinished`。
- `ExportCollection.cs`：新增 `protected static DeletePartialExportFiles(filePath, fileSystem)`（删内容文件 + 同名 .meta，失败降级为日志）；`ExportAsset` 失败时清理并重抛。
- `AssetExportCollection.cs`：`Export` 失败时清理并重抛。覆盖所有走 `ExportInner` 的集合（纹理/音频/模型/YAML 音频与着色器等）与走 `ExportAsset` 的集合；直接重写 `Export` 的场景/脚本/Manager/EditorBuildSettings/UserAsset/Unreadable/Unknown 未覆盖（已知缺口）。
- 构建验证：`dotnet build` 单工程 + GUI.Free 均 0 error（`dotnet build-server shutdown` 可解 CS2012 文件占用）。

## 功能：AssetRipper.Logging 日志加时间戳
- 需求：每条日志打印时加入时间戳。确认范围=ConsoleLogger + FileLogger（本地时间），CleanFileLogger 不动（无人调用且语义"干净"）。
- 实现：`Logger` 新增 `IncludeTimestamp`（默认 true，可关）与内部 `CurrentTimestamp`；在 `Log(LogType,LogCategory,string)` 锁内赋值一次（锁外先算 `DateTime.Now:HH:mm:ss.fff`），保证控制台/文件同一行时间一致且只算一次。ConsoleLogger、FileLogger 的 `Log` 复用 `Logger.CurrentTimestamp` 前缀。
- 仍保持零依赖（仅用 BCL `DateTime`）。`dotnet build` 单工程 0 警告 0 错误。
