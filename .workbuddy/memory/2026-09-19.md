## 分析：Load 后 699.6 MB 的 Byte[] 占用来源（Nikki4 端urance 资源区，日志 20260919_040622）

### 结论
几乎全部是 **FileStream 的 4 KB IO 缓冲区**，不是资产数据。

- `System.Byte[]` 178,611 个 / 699.6 MiB（ToMegabytes 用的是 /1024/1024，即 MiB）
- 同一快照：`System.IO.FileStream` 175,448、`BufferedFileStreamStrategy` 175,448、
  `SyncWindowsFileStreamStrategy` 175,448、`SafeFileHandle` 175,451 → 与 Byte[] 数量几乎 1:1
- 175,448 × 4096 B = **685.3 MiB = 总量的 98%**；剩余 3,163 个 Byte[] 平均 4.7 KB
- 反证：第二次快照（Process 完成）Byte[] 从 178,611 涨到 533,707，却只多占 22.4 MB（新增的平均 66 B），
  说明 4 KB 那批在第一次快照前就已全部落地且不再增长
- 数量对齐：`SerializedFile 88,766 + ResourceFile 88,724 = 177,490`；
  `FileStream 175,448 + MemoryStream 2,042 = 177,490` → 每个 bundle 条目一个底层流

### 根因链
`FileStreamBundleFile.ReadFileStreamData` → `BundleFileBlockReader.ReadEntry` → `CreateStream(size)`
→ 因为 **本地把 `MaxMemoryStreamLength` 改成了 1024 字节**（注释仍写着 50 MB），
所有 >1 KB 的条目都走 `SmartStream.CreateTemp()` → `FileStream(..., bufferSize: 4096, DeleteOnClose)`。

### 提交史（重要，别再当成上游默认值）
- `b78861b08`（Revert）时还是 `50 * 1024 * 1024` / `30 * 1024 * 1024`
- `ebf30da8f`（feat(memory): 添加内存诊断日志）改成 `1 * 512 * 1024`
- `38f5fdc40`（测试导出）改成 `1024`，`MaxPreAllocatedMemoryStreamLength` 改成 `1023 `（残留空格，明显手工编辑）

### 候选修复（未实施，等确认）
1. `SmartStream.CreateTemp()` 的 `bufferSize` 改 0/1 → 立即省 ~685 MB，最简单
2. 阈值改回真实 MB 级（如 8~50 MB），小条目留内存，只有大条目落盘
3. 结构性：压缩块按块解压后共享，条目用 CreatePartial 指向块内区间，把 17.5 万临时文件降到块数量级

## 实施结果（方案 C：整包解压共享 + 修复扫描重复）

### 改动
1. `FileTypeScanner.FilterByHeader` 由「序列化文件 OR 资源包」改为按本次收集的种类判定（传入 headerPredicate）。
2. `HeaderProbe.MatchesSerializedFile` 增加 `fileSize` 参数并加上「头部声明大小 == 实际大小」比对。
   —— 这是重复加载的真正根因：UnityFS 的前 12 字节恰好满足旧判据，被同时当成序列化文件与资源包收集，
   而 `GameBundle.FromPaths` 按内容分派，两个条目都被当 bundle 读一遍。
   `FileTypeScanner` 顺带把 `EnumerateFileInfos` 拿到的真实大小传给判定（批量读头只有 32 字节，拿不到真实大小）。
3. `BundleFileBlockReader` 新增整包解压共享：`DecompressAllBlocks()` 把所有块解压进一条流，
   `ReadEntry` 返回 `shared.CreatePartial(entry.Offset, entry.Size)`。实测 400/400 样本中
   条目偏移首尾相接且从 0 开始、条目总长 == 块解压总长，因此该假设成立。
   保留单块未压缩的零拷贝快速路径；整包解压失败时回退到原来的逐条目复制（保留坏块只影响用到它的条目的语义）。

### 实测（`body` 目录 468 个 bundle，同一台机器 A/B）
| 指标 | 逐条目复制（原逻辑） | 整包共享 | 变化 |
|---|---|---|---|
| FileStream | 936 | **468** | 2/包 → 1/包 |
| SafeFileHandle | 939 | 471 | 减半 |
| Byte[] | 1,992 / 12.8 MB | 1,049 / 9.0 MB | −30% |
| 加载耗时 | 98.3 s | **23.8 s** | 快 4.1× |

扫描重复修复后：目标目录 44,383 个文件 → 收集到 ~44,383 条（原先 88,766，正好 2 倍）。
据此推测全量：`FileStream` 175,448 → ~44,383，`Byte[]` 缓冲区 685 MB → ~178 MB。

### ⚠️ 环境注意
这台机器在 04:06 之后整体慢了约 20 倍（同样的原逻辑从 2 ms/文件变成 221 ms/文件），
疑似 Defender 对 `0Bins/.../Debug/temp/` 下大量 DeleteOnClose 临时文件的实时扫描。
**跨时段比较绝对耗时没有意义，只能做同时段 A/B。**

## 环境备注
- 该 bash 沙箱缺 `head`/`grep`/`find`（coreutils 不全），管道到 Grep 类命令会 127；用工具自带 Grep，或 PowerShell
- PowerShell 工具不回显 stdout，要把结果 WriteAllLines 到临时文件再 Read
- HTTP 驱动 GUI 做复现时，`/Settings/Update` 的表单字段名是 **不带类名前缀**的 `nameof(...)`，
  即 `GameType=Nikki4&MemoryBreakdownMode=ClrMd`，写 `ImportSettings.GameType` 会静默无效（返回 302 但不生效）。
  `/LoadFolder` 用 `Path=`。加载是同步阻塞的，客户端必须只发请求不读响应，否则超时会把请求打断。
- 诊断口径没有环境变量，只能靠设置；日志开头的 `Configuration Settings:` 是启动时打印的，
  不能用来判断本次 POST 是否生效——要看实际输出的是「序列化数据」还是「整堆」。
