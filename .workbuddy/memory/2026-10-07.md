## 新功能：设置页支持选择导出路径

### 需求
用户希望在**设置页**直接选定导出路径（此前只能在导入完成后的导出页填），配合"导入后自动导出"实现
"配一次 → 选文件夹 → 自动导完"的闭环。

### 设计取舍
- 新增 `ImportSettings.AutoExportPath`（string?），与 `AutoExportKind` 并列放在导入区：
  设置页只在未加载资源时可编辑，放 Import 侧才能在导入前配好。
- **优先级抽成纯函数** `GameFileLoader.ResolveBasePathFromCandidates(configured, remembered, importPath)`：
  设置页配置 → 上次实际使用（`LastExport.ExportPath`）→ 导入目录的**同级**目录。
  之所以拆出纯函数，是因为公开重载要读全局状态、在单测里会受磁盘上的设置文件影响，无法给出稳定预期。
- 导出页预填改用 `GameFileLoader.PreferredExportPath`（同样的前两级，**不做第三级回退**）：
  导出页拿不到导入目录，凭空填一个用户没选过的目录只会误导。
- 手动导出统一走 `GameFileLoader.RememberExportPath(path, createSubfolder)`：同时写设置项与 `LastExport`，
  前者让两个页面立刻显示同一路径，后者始终落盘（不受"保存到磁盘"开关影响）。
  此前 `Commands` 里两处各写三行，现在收敛成一处。
- 前端注入变量 `window.__lastExportPath` 更名为 `window.__exportPath`（语义已不再是"上次导出"），
  同步改了 `commands_page.js`。

### 教训

## 环境备注（本次新踩）
- **后台进程在两次工具调用之间会被回收**：`Start-Process` / `cmd &` / `( cmd & )` 都撑不过一次调用边界。
  端到端 HTTP 验证必须在**同一个 Bash 调用**里完成"启动 → 请求 → 收结果 → kill"。
- `Select-Object -First N` 接在进程输出管道上会在 N 行后关掉管道并终止进程。
- **Python 会改写字符串字面量里的反斜杠为正斜杠**（写文件时生效）：`r"D:\a\b"` 落盘变 `D:/a/b`。
  要写 Windows 反斜杠路径用 PowerShell + .NET `WriteAllText`。
- 应用自己写的 `AssetRipper_*.log` 是 UTF-8；`> out.txt` 捕获的 stdout 是 GBK —— 读日志要选对编码。
- `Configuration Settings:` 块是 `LoadAndProcess` 里打印的（**不是启动时**），要看必须触发一次加载。
- `/Settings/Update` 会**整体重写所有布尔项**（`form.ContainsKey`）→ 只提交部分字段会把其它复选框静默清成 false。
  验证配置时要么提交完整表单，要么直接改 JSON 文件。

## 调查：导出 prefab 的 m_Controller guid 在两批导出间变化（80a2 ↔ b61e）

### 现象
`mainstory_nightmare_QTE_bg_1.prefab` 的 `m_Controller`：
- C:\Unity\Nikki4（10/2-3 批次，源 = Nikki4Out/AssetRipper_export_20261002_194043 的 Assets）：guid `b61e87769a3bfae8a7446867fb7d293b`
- D:\UserData\ex\AssetRipper_export_20261004_134524（10/4-5 批次）：guid `80a2b5621ca828cadb6704d84cc45a00`
- 同目录下 `mainstory_nightmare_QTE_fazhen_Light.prefab` 也有同类变化（e9b26ed4→011828d6）；autoui/mainstory 目录 0 变化。

### 硬结论（游戏数据侧铁证）
- 游戏数据里存在**两个同名 controller 副本**（同 pathID 8225008247098789000，各带同名 clip 4153492354410969446，内容不同）：
  - **X1**：`art/ui/prefabs/autoui/mainstory/mainstory_angelandevil_qte_bg_1.prefab` bundle 内（cab `CAB-b5e1726a…`，含 NN4AnimationEvent MonoScript；clip 为**明文**曲线路径 Roleroot_1，导出为无 _0 的 .controller/.anim，**guid=b61e/a3455e8c**）
  - **X2**：`art/ui/animations/mainstory/mainstory_angelandevil_qte_bg_start.controller` bundle（cab `CAB-d1a2c184…`；clip 为**混淆**曲线路径 path_0x…，导出为 _0 文件，**guid=80a2/b37d82a5**）
  - 全量扫描 art(333104 文件)+bin/Data+assetbundles：两个 cab 名各只出现在这 1 个文件里，**无第三副本**。
- prefab 游戏数据里 `m_Controller=(fileID=12, pathID=8225008247098789000)` → externals[11]=`archive:/CAB-d1a2c184…` → **X2**；assetbundledeps.json 亦指向 animations 的 controller 路径。
- **∴ 80a2（新导出）与游戏原始依赖一致 = 正确；b61e（旧批次）指向了 autoui 的副本。**
- 两批导出的 guid 映射本身**稳定**（prefab meta guid 两批都是 d772637d…；b61e/80a2 文件名↔guid 关系不变）→ **确定性 GUID 在正常工作**；变的只是"prefab 的 m_Controller 解析到哪个副本"。
- **不是去重问题**：两副本内容不同（m_Motion→不同内容 clip），去重未合并；两批里两个 controller 文件都导出。autoui prefab 两批都引用 b61e（与其同 cab 引用一致，稳定）。

### 遗留（未闭合）
- F1 为何解析到 X1 未能 100% 归因：按代码 `ResolveCollection("cab-d1a2c184…")` 名字唯一、解析应确定；依赖失败只会得到 missing（fileID:0）而非 X1。可能：旧批次用了不同构建（含未提交改动）/F1 资产被工具改过/依赖映射文件（DependencyMap）状态不同。**待用户用当前构建重导复现**（若仍 b61e 或又变 → 可复现深挖）。

### 技术要点（闪暖数据格式，复用于后续排障）
- `assets/art/**` 下"一资源一 UnityFS bundle"；cab 名= bundle 内 node 名 `CAB-<32hex>`；`FixFileIdentifier` 后小写为 `cab-<hex>`（= 集合名 NameFixed）。
- externals 的引用格式 `archive:/CAB-<hash>/CAB-<hash>` → Fix 后 `cab-<hash>`。
- **文件级依赖解析**（`FindDependency`）三条路：①`_filesIndex`（键=文件基名去扩展名小写，匹配不上 cab-hash）②`join(dataPath, dep)`（同前）③**`DependencyMap.TryResolve`**（依赖映射文件的 d 键=SerializedFile.NameFixed —— **唯一能解析 `cab-<hash>` 的途径**）。**无 DependencyMap 时闪暖 archive:/CAB-* 依赖全部解析不了** → 导入设置里的"依赖关系文件路径"极关键。
- 手写 UnityFS 解析器（python+lz4）要点：header 后 **16 字节对齐**读 blocksInfo；数据区**紧跟** blocksInfo 之后（不对齐）；blocks 表字段顺序 **未压缩在前** `u32 u32 u16`；sfVer=21 时 types 段= int32+bool+int16+(cid==-1||114||sti>=0 时 16B scriptID)+16B oldTypeHash+typeTree(nodesCount,stringBufSize,nodes×32B,stringBuf)+**typeDeps(int32 count+4×n)**；objects=align4+int64+u32+int32+int32(typeIndex)；externals 每条= AssetPath 串+16B guid+int32 type+PathNameOrigin 串；Animator(m_Controller) 数据布局: (m_GameObject 12B)(m_Enabled 1+3pad)(m_Avatar 12B)(m_Controller 12B)。
