## 新增：真实托管堆字节数估算（替代序列化字节数）
- 需求升级：用户要统计 Assets 中已反序列化 IUnityObjectBase 的**真实托管堆字节数**，而非序列化数据字节数。
- 新增 `Source/AssetRipper.Export.UnityProjects/Memory/ManagedSizeCalculator.cs`：用反射遍历对象图估算托管堆占用（对象头 + 字段 + 数组 + 字符串 + 引用对象），`HashSet<object>`(ReferenceEqualityComparer) 跨资产共享去重，保证共享引用只计一次。
  - 关键防爆炸：遍历到 `AssetRipper.Assets.Collections` / `AssetRipper.Assets.Bundles` / `AssetRipper.Import.Structure` 命名空间类型及 `AssetInfo` 时**只计指针、不再向下递归**，避免从任一资产牵出整个 GameBundle。
  - 数组：值类型元素按 `ValueTypeShallowSize × 元素数`（不逐个迭代，避免 byte[]/Vector3[] 装箱爆炸）；引用类型元素才逐个 Walk。字符串按 `头+长度*2`。字段信息按类型缓存（`ConcurrentDictionary`）。
- `ExportHandler.LogResourceBreakdown` 改为两种模式，由环境变量 `RURI_MEM_BREAKDOWN_MODE` 控制：`live`=真实托管堆估算；其它（默认）= 原快速序列化字节数。日志行标签相应变为"托管堆(反射估算)"/"序列化数据"。
- 默认仍为快速模式（真实估算很重，大项目可能卡数分钟，故 opt-in）。已编译通过。

## 新增：ClrMD 整堆快照按类型聚合（第三种统计口径）
- 需求：`ExportHandler.cs` 的 `LogResourceBreakdown` 接入 ClrMD，做**整堆快照**并按类型聚合。
- 方案：`RURI_MEM_BREAKDOWN_MODE` 增加第三个取值 `clrmd`（与前两者互斥，走独立分支 `LogHeapSnapshotBreakdown`），统计的是整个进程 GC 堆，累加值可与 `Logger.LogMemoryDiagnostics` 的托管总量对齐。
- 新增 `Source/AssetRipper.Export.UnityProjects/Memory/ClrMdHeapAnalyzer.cs`：`TryAnalyze(dumpPath, maxObjects, out result, out error)`，任何失败都返回 false 不抛异常。
  - 取数：`DataTarget.CreateSnapshotAndAttach(ProcessId)`（快照=一致镜像；**直接 AttachToProcess(suspend:false) 是 ClrMD 明确不支持的用法**，仅作非 Windows/快照失败兜底）→ `ClrVersions[0].CreateRuntime()` → `Heap.EnumerateObjects()` → `obj.Type.Name` / `obj.Size`。
  - 环境变量：`RURI_MEM_BREAKDOWN_DUMP`（改用 dotnet-dump 产物）、`RURI_MEM_BREAKDOWN_MAX_OBJECTS`（超大堆抽样）。
- 包选型：`Microsoft.Diagnostics.Runtime` **3.1.512801**（csproj 有注释说明）。4.x 会额外拖入 `Azure.Identity` 依赖链，而这里只用"自快照"一条路径；3.1 只依赖 `Microsoft.Diagnostics.NETCore.Client`，Debug 输出增加约 800KB。
- Unity 资产归并视图：生成类的全名是 `AssetRipper.SourceGenerated.Classes.ClassID_<数字>.<类名>`（该包是 NuGet 依赖 `AssetRipper.SourceGenerated` 1.3.14.2，**仓库内没有源码**），"ClassID_" 后的数字就是 Unity ClassID，据此复用 `GetTypeName` 映射，无需反射生成程序集。手写专属类（如 `Shader_Nikki4`）不在该命名空间下，会落到"其它"。
- 日志分四段：按字节 Top25、按数量 Top10、Unity 资产归并、命名空间首段分组（编译器生成的名字以 '<' 开头，归入"其它"）。

## 重构：内存诊断整体搬进 Logger + 增长自动拆解
- 需求：① 这套功能放 `ExportHandler` 不合适，移到 `Logger` 类；② `Logger.LogMemoryDiagnostics` 在内存大幅增长时自动打印一次统计。
- **关键约束（决定了方案形态）**：`GameData` 在 `AssetRipper.Processing` 而非 `AssetRipper.Import`，`Logger` 在 Import，所以 Logger **不能**引用 GameData（否则 Processing↔Import 循环依赖）。因此没有采用"注册静态 Func<collections> 提供者"（那还会让静态字段把 GameData 钉住、Reset 后泄漏），而是给 API 加**显式参数**：
  - `Logger.LogMemoryDiagnostics(string stage, IEnumerable<AssetCollection>? collections = null)`
  - `Logger.LogResourceBreakdown(IEnumerable<AssetCollection>? collections, string stage)`
  - 默认/live 口径需要 collections，缺失时打一行明确提示；`clrmd` 口径不需要（统计的是进程 GC 堆），因此没有数据源也能工作。
- 文件落位：`Logger` 改 `partial`，诊断成员集中在 `AssetRipper.Import/Logging/Logger.MemoryDiagnostics.cs`（原来的 `LogMemoryDiagnostics` 从 Logger.cs 移出）；两个纯分析器搬到 `AssetRipper.Import/Memory/`（`ManagedSizeCalculator`、`ClrMdHeapAnalyzer`）；`Microsoft.Diagnostics.Runtime` 包引用从 `AssetRipper.Export.UnityProjects.csproj` 移到 `AssetRipper.Import.csproj`（该 csproj 因此恢复原样）。`ExportHandler` 只剩一个私有转发 `LogMemoryDiagnostics(gameData, stage)` + 两处显式 `Logger.LogResourceBreakdown(...)`。
- 增长自动拆解：阈值 `RURI_MEM_BREAKDOWN_GROWTH_MB`（默认 **1024**，≤0 关闭）。首个诊断点只建基线（避免把加载前存量算成增长）；每次拆解结束（含显式调用）都把基线前移到当前托管堆，保证**同一段增长只报一次**。触发时先打一行 `[内存诊断] ↑ ...` 说明原因，再走正常拆解。
- 健壮性：`LogResourceBreakdown` 内 catch 所有异常并降级为 Warning——自动触发发生在 `Process` 中途，诊断失败不能中断导出。
- 验证（临时 harness，见当日验证手法）：`TryAnalyze` 在 Import 程序集下可用；ClassID 映射/上限解析正常；mode=默认 + collections=null 给出提示；空集合能跑通聚合；mode=clrmd 无需 collections；**增长逻辑实测**：建基线不触发 → +58.5MB 触发 → 同段不重复 → 再 +59.3MB 再触发 → 阈值归零后不再触发。全解决方案 Rider 构建 `buildIsSuccess: true`。

## 重构（续）：内存诊断独立成 `AssetRipper.Diagnostics`
- 起因：用户问"MemoryDiagnostics 依赖 Assets，能否直接放进 `AssetRipper.Assets`"。**结论是不行**，验证依据：
  ① `ClassIDType` 在 NuGet 包 `AssetRipper.SourceGenerated` 里，而 `AssetRipper.SourceGenerated.dll` 引用 `AssetRipper.Assets.dll`（生成类实现 `IUnityObjectBase`；在 65MB 的 dll 里能搜到 `AssetRipper.Assets.Metadata.*` 这类 TypeRef），Assets → SourceGenerated 必然成环。nuspec 里 SourceGenerated **没有声明任何依赖**（它把 Assets/IO.Files/Primitives 留给消费方提供），所以环不会在 NuGet 阶段被发现，只会在编译期炸。
  ② `IUnityObjectBase.ClassName` 只能救 live 路径的命名；默认（快速）口径只拿到 `(ClassID, size)`，要绕开枚举就得运行时反射 `Type.GetType("AssetRipper.SourceGenerated.ClassIDType, AssetRipper.SourceGenerated")`。
  ③ 更要紧的是 ClrMD：`MemoryDiagnostics`/`ClrMdHeapAnalyzer` 会把 `Microsoft.Diagnostics.Runtime` + `Microsoft.Diagnostics.NETCore.Client`（约 800KB）带进最底层模型程序集，所有引用 Assets 的工程都会被动继承，而诊断只有导出管线用。
- 采纳方案：新建 `AssetRipper.Diagnostics`（依赖 Logging + Assets + SourceGenerated 包 + ClrMD 包），把 `MemoryDiagnostics`/`ClrMdHeapAnalyzer`/`ManagedSizeCalculator`/`TypeAggregate` 从 `AssetRipper.Import/Memory/` 整体搬过去，命名空间 `AssetRipper.Import.Memory` → `AssetRipper.Diagnostics.Memory`；`Microsoft.Diagnostics.Runtime` 包引用同期从 Import 移出（Import 因此不再依赖 ClrMD）。
- `ExportHandler`（唯一调用方）改 `using AssetRipper.Diagnostics.Memory;`，`Export.UnityProjects.csproj` 加 Diagnostics 引用（顺手把上一轮脚本追加在文件末尾的 Logging ItemGroup 合并进主引用组并排序）。
- 验证：`dotnet build AssetRipper.slnx` 0 error；harness 读程序集引用表实测 —— `Diagnostics` 引用 `Microsoft.Diagnostics.Runtime, AssetRipper.Assets, AssetRipper.IO.Files, AssetRipper.SourceGenerated, AssetRipper.Logging`；**Import 是否还引用 ClrMD = False**；Assets 仍无 Cpp2IL/ClrMD；四张榜（含平均榜）、整堆视图、增长触发全部照旧。
