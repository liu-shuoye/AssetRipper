### 关键时序坑（下次务必注意）
`IUnityObjectBase.MainAsset` 由 `AssetGroup.SetMainAsset()` 赋值，调用方是：
`PrefabProcessor`(链上第19) / `SpriteProcessor`(20) / `ScriptableObjectProcessor`(21)，
以及 `SceneDefinitionProcessor`(12)、`MainAssetProcessor`(14, 字体/地形)、`AudioMixerProcessor`(16)。
→ 任何依赖 `MainAsset` 的路径逻辑**不能写进 `OriginalPathProcessor`(13)**，必须新处理器注册在链尾。
`MainAsset` 只覆盖：预制体/场景层级里的 GameObject + 组件 + PrefabInstance、SpriteInformationObject、ScriptableObjectGroup；
**AnimationClip / Mesh / Material / AnimatorController 的 MainAsset 为 null**，只能靠 bundle 主资产回退。

### 资源包主资产判定
`bundle.Container` 里 `Asset.FileID == 0`（非共享资产）且 `EnsurePathNotRooted` 非空的条目，优先取文件名（去扩展名）与 bundle 名相同的那个，否则取第一个。
取到后用 `Path.ChangeExtension(path, null)` 得到同名文件夹（如 `Assets/a/b/yyy.prefab` → `Assets/a/b/yyy`）。

## perf(import): 优化大规模项目文件扫描（30w 文件从半小时降至秒级）

**诊断结论（有日志证据，非猜测）**：`PlatformGameStructure.CollectFiles` 的耗时**不在目录枚举**，
而在对**每个文件**调用一次 `SerializedFile.IsSerializedFile(path, fs)` / `BundleHeader.IsBundleHeader(path, fs)`
——每次都要开关一次流。证据：`AssetRipper_20260913_063904.log` 里 41000 个 bundle 只占 7 行日志（枚举极快），
但整阶段耗时约 30 分钟。

**三层优化（用户决策「三者都做」）**
1. **名称+体积预筛**（零 syscall 排除）：`FileTypeScanner` 的 `DefinitelyNotUnityContent` 集合按扩展名排掉
   图片/音频/视频/文本/字体等；再用 `SerializedFileMinimumSize`(0x10+13) / `BundleMinimumSize`(0x14) 排掉过小文件。
2. **批量并发读文件头**：候选文件统一走 `FileSystem.BatchReadHeaderPrefix`（线程数可配置，
   `LocalFileSystem.DefaultHeaderReadConcurrency = Clamp(ProcessorCount, 1, 16)`），
   判定交给纯函数 `HeaderProbe`（可脱离磁盘单测）。
3. **扫描结果落盘缓存**：`FileScanCache` 按**目录指纹**（文件数 + 最后写入 UTC ticks）校验，
   指纹不符即该目录重扫，**绝不静默信任**；版本或 RootPath 不符则整体丢弃。默认关闭
   （`PlatformGameStructure.ScanCacheEnabled` / `ScanCachePath`），避免产生用户未预期的文件。

**关键约束与坑**
- `AssetRipper.IO.Files.csproj` **没有任何 ProjectReference**（只有 NuGet 包），
  因此**不能引用 `AssetRipper.Logging`** → 所有诊断必须用可选 `Action<string>?` 回调传出参数。
- `System.IO.File.OpenRead` 的流池是**进程级串行**的，多线程用它会互相排队、反而更慢；
  所以 `LocalFileSystem` 走 `new DirectoryInfo(path).EnumerateFiles()` 直接拿 名称+体积，
  且基础类默认实现保持**串行**，只在 `LocalFileSystem`/`VirtualFileSystem` 覆写并发版本。
- 生成类 `FileSystem.g.cs` / `LocalFileSystem.g.cs` / `VirtualFileSystem.g.cs` 标着
  "Auto-generated, do not modify"，但其中**可以承载非生成代码体**（如 `LocalDirectoryImplementation Create/Delete`）。
  规则：**抽象成员改动写 `.g.cs`；具体覆写写手写文件**（否则下次再生成会丢）。
- `SerializedFileHeader.IsSerializedFileHeader` 用 `Enum.IsDefined(generation)`，
  但 IO.Files 拿不到生成的 `FormatVersion` 枚举 → `HeaderProbe.IsKnownFormatVersion` 用
  范围判断（`is >= 0 and <= 255`）兜底，真正区分靠长度约束。
- 原 `CollectAllSerializedFiles` 里按名字去重是**死代码**：`GameStructure.InitializeGameCollection`
  调 `GameBundle.FromPaths(...)` 只用 `Files.Values()`（只要路径，名字被丢弃）→ 改成普通 `AddRange` 安全。

## ⚠️ 仓库事故：alpha 顶端提交对象丢失并已修复

**症状**：执行 `git stash push --include-untracked` 时报
`error: invalid object ... for '.workbuddy/memory/2026-07-31.md'`，随后**所有 git 命令**都报
`fatal: not a git repository`。

**根因**（逐步定位）：`.git/` 结构本身完好（HEAD/config/packed-refs/objects/logs 都在），
但 **`.git/refs/` 整个目录不存在** → git 无法把目录识别为仓库。
更深一层：**`.git/objects` 里 loose_objects = 0**，最近的 loose 对象被清掉了。
pack 文件（3 个，共 ~463MB）仍在且可读，含 4352 个 commit。

**修复步骤（无损，全部依据 git 自身记录）**
1. 从 `.git/logs/refs/**` 的 reflog **最后一行**取每个 ref 的 SHA（格式：`<old> <new> <who> <when>\t<msg>`，取第 2 个字段）。
   ⚠️ 坑：reflog 相对路径**已经以 `refs/` 开头**，拼到 `.git/refs/` 下会变成 `refs/refs/heads/...`，必须去掉一层。
2. 重建 `.git/refs/heads/**` 写回 SHA。
3. `alpha` 的顶端 `c2226003` 恰好是**丢失的那个 loose commit**（它的父 `8b5bacbf` 在 pack 里，可读）
   → `git update-ref refs/heads/alpha 8b5bacbf` 把分支指回有效父提交。
4. `git read-tree <有效commit>` 重建索引（`reset --mixed` 会因索引引用已丢失对象而失败）。
5. 工作区文件**全部完好**（先做了双份备份），重新 `git add` + `commit` 生成新顶端 `b0d56ee41`，
   把丢失提交的语义（移除 `art\audio` 跳过、`CollectStreamingAssets` 转私有+中文日志）
   连同本次优化一起写入提交说明。

**最终状态**：`git fsck` 中 `OTHER_errors = 0`（可达历史无缺失对象）；
残留 244 条 reflog 错误 + 6 个 `optimize/*` 分支的 `invalid sha1 pointer`
——**均为既存问题**（reflog 时间戳是数月前，那些分支早已指向被回收的对象），与本次事故无关。
`alpha` / `master` 两个在用的分支均健康。

**教训**：此仓库的 `.git` 处于**易失状态**（loose 对象会被外部清理、多个陈旧分支已断）。
后续在这个仓库里做任何 git 操作前，**先把改动文件复制一份到仓库外**；
不要依赖 `git stash`（它需要扫描全部对象，一遇缺失就整体失败）。
